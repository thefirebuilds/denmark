# Trip telemetry review

In **Trip Ledger**, open a trip, then select **Review telemetry** below the route map. The review loads on demand and requires both the existing trip-read access and `telemetry.read` permission.

The timeline has paged views for all stored snapshots and all stored signal values attributed to that trip. Nothing is downsampled for review; use Next/Previous to traverse 50-record pages. Provider, observed-time range, minimum snapshot speed (mph), and signal-name filters narrow the records. Display times use America/Chicago with a timezone abbreviation; filter inputs use the browser's local timezone. Exported normalized timeline times have UTC offsets. Snapshots use provider speed time, then vehicle/location time, then receipt time when no observation time exists. Signal rows use their signal timestamp, falling back to receipt time. Received time is always shown separately.

The scope is **stored trip attribution**, matching the existing path association. Unassigned telemetry or telemetry attributed to another trip is not guessed into this review based on a nickname or time overlap. Readings can be stale and timestamped outside the reservation even when their snapshot is associated with it; the view marks that case. An early actual return is shown in summary data but does not rewrite stored associations or claim who was driving.

Snapshot speed is normalized to mph by the existing collectors. Signal values retain their stored/provider units and are not relabeled as mph. Max sampled speed and the number of samples at/above 80 mph include only speed readings with a known observation time inside the scheduled trip window. They describe stored observations, not separate incidents, duration above a threshold, or violations of posted road limits. Repeated polling may store the same old reading more than once. Changing the minimum speed is an investigation aid, not a determination of unsafe driving.

**Collection limitation:** the current Bouncie collector polls vehicle snapshots and the DIMO collector stores requested signals. Denmark does not currently ingest a dedicated impact, collision, hard-braking, or aggressive-driving event feed. It cannot reconstruct those events from sparse polling or recover events never received. Inspect snapshot fields, raw payloads and signal names for whatever a provider actually supplied. Matching impact/driving field names are highlighted as raw keyword matches, with false/zero values preserved; they are not verified incidents. Missing matches do not establish that no incident occurred.

Snapshot inspection shows all normalized snapshot fields and the retained provider payload, using the archive first and legacy inline payload as a fallback. Raw timestamps are shown as stored with their existing DIMO Chicago/Bouncie UTC timestamp conventions explained in the view. Missing raw payloads are explicitly labeled. Legacy raw retention defaults to 90 days; archive retention is separately configurable and is not pruned by default. Normalized snapshots and signal values can therefore survive after a raw payload is gone.

**Export this page (JSON)** saves the current filtered page, filter values and summary. **Export snapshot (JSON)** saves the inspected normalized snapshot and raw payload. These buttons are explicitly scoped; a page export does not pretend to be a full-trip export. Credentials/authentication fields are redacted recursively from all returned/exported payloads. No payloads or guest details are written to logs by these endpoints.

The feature adds read-only, trip-scoped queries with bounded pages and lazy raw-payload loading; it does not contact provider APIs, add polling jobs, migrate schemas, backfill associations, or change retention. Deploy the updated backend and frontend together. Existing database schema contains the snapshot, signal and raw archive tables.
