# Trip telemetry review

In **Trip Ledger**, open a trip, then select **Review telemetry** below the route map. The review loads on demand and requires both the existing trip-read access and `telemetry.read` permission.

The timeline has paged views for all stored snapshots and all stored signal values attributed to that trip. Nothing is downsampled for review; use Next/Previous to traverse 50-record pages. Provider, observed-time range, minimum snapshot speed (mph), and signal-name filters narrow the records. Display times use America/Chicago with a timezone abbreviation; filter inputs use the browser's local timezone. Exported normalized timeline times have UTC offsets. Snapshots use provider speed time, then vehicle/location time, then receipt time when no observation time exists. Signal rows use their signal timestamp, falling back to receipt time. Received time is always shown separately.

The scope is **stored trip attribution**, matching the existing path association. Unassigned telemetry or telemetry attributed to another trip is not guessed into this review based on a nickname or time overlap. Readings can be stale and timestamped outside the reservation even when their snapshot is associated with it; the view marks that case. An early actual return is shown in summary data but does not rewrite stored associations or claim who was driving.

Snapshot speed is normalized to mph by the existing collectors. Signal values retain their stored/provider units and are not relabeled as mph. Max sampled speed and the number of samples at/above 80 mph include only speed readings with a known observation time inside the scheduled trip window. They describe stored observations, not separate incidents, duration above a threshold, or violations of posted road limits. Repeated polling may store the same old reading more than once. Changing the minimum speed is an investigation aid, not a determination of unsafe driving.

**Collection limitation:** automatic Bouncie collection polls snapshots and DIMO collection stores requested signals. Active DIMO vehicles are also checked every 15 minutes for provider-reported `safety.collision` events. Other DIMO event history can be imported on demand as described below. Denmark cannot reconstruct an accident from sparse polling or recover an event the provider never recorded or no longer retains. Matching impact/driving field names in raw snapshots are keyword matches, with false/zero values preserved; they are not verified incidents. Missing matches do not establish that no incident occurred.

Snapshot inspection shows all normalized snapshot fields and the retained provider payload, using the archive first and legacy inline payload as a fallback. Raw timestamps are shown as stored with their existing DIMO Chicago/Bouncie UTC timestamp conventions explained in the view. Missing raw payloads are explicitly labeled. Legacy raw retention defaults to 90 days; archive retention is separately configurable and is not pruned by default. Normalized snapshots and signal values can therefore survive after a raw payload is gone.

**Export this page (JSON)** saves the current filtered page, filter values and summary. **Export snapshot (JSON)** saves the inspected normalized snapshot and raw payload. These buttons are explicitly scoped; a page export does not pretend to be a full-trip export. Credentials/authentication fields are redacted recursively from all returned/exported payloads. No payloads or guest details are written to logs by these endpoints.

**Export all telemetry (JSON)** downloads every stored snapshot, signal value and retained raw payload attributed to this trip, ignoring the current page and filters. It includes summary, units/timestamp conventions, record bounds and exported counts. The backend streams keyset batches (50 snapshots or 100 signals), honors download backpressure and stops on disconnect; it does not assemble the whole trip in server/browser JavaScript memory or hold a pool client during the download. Record IDs are capped at export start, but concurrent edits or retention can still change records; this is not a transactional snapshot. A successful file ends with `"complete":true`; interrupted/failed streams are incomplete JSON and must not be treated as a complete export. Existing trip/telemetry read permissions apply. Missing/pruned raw payloads remain null; unassigned telemetry is excluded. Deploy the backend and frontend; no migration is required.

Telemetry reads and exports remain local, trip scoped and bounded. The manual incident import and scheduled collision check contact DIMO. Deploy the updated backend and frontend together. Startup automatically creates the incident, import-history, collision-monitor and checkpoint tables using the existing schema-ensure pipeline. The deployment database role needs its usual CREATE TABLE/INDEX permission. Imported trip events persist until their trip is deleted; vehicle collision records/checkpoints persist until their vehicle is deleted. Existing snapshot/raw-payload retention is unchanged.

## Automatic collision alerts

The existing backend scheduler runs `dimoCollisions` every 15 minutes (an application timer, not an Ubuntu crontab). Its first run is staggered by `SCHEDULER_INTERVAL_OFFSET_STEP_MS * 4`, normally three minutes after scheduler start. It polls active vehicles with DIMO token IDs sequentially, even when there is no active trip, requesting only `safety.collision`. DIMO integration must be enabled. Set `DIMO_COLLISION_POLL_ENABLED=false` to disable this job; no new credentials or dependencies are needed. Timers are unreferenced and cleared on shutdown, and in-flight provider calls are aborted. Concurrent runs in the same process are skipped; collisions and SMS claims are deduplicated in Postgres across restarts/processes.

The first check looks back 24 hours, not all historical trips. Later checks overlap the saved checkpoint by 24 hours to catch delayed provider records. Downtime catch-up advances by at most 24 hours per successful poll (queries span at most 48 hours including overlap). Failed vehicle lookups retain their checkpoint and do not stop other cars being checked. Delays exceeding the overlap can still be missed; use manual imports for older history. Database-pressure deferral uses the existing scheduler reserve rules. Provider auth/requests use the existing event-import deadline and response bounds; no database client or transaction is held while waiting on DIMO or SMS.

For each new source/timestamp collision, one transaction saves a durable vehicle collision, an unread `collision_detected` message, and a trip telemetry event if exactly one non-canceled reservation matches the vehicle's exact Turo ID and event timestamp. No nickname or nearest-trip guessing is used. Missing/overlapping reservations still produce a vehicle queue warning and text without a trip assignment; a later overlapping poll can attach a newly resolved unique match. Tracker reassignment does not move old collisions to another vehicle. Trip ledger rows, trip drawers and active trip cards show a **Collision detected** flag based on stored collision-event records. Flags persist when a queue message is cleared. Provider events and manual imports can describe the same incident in multiple records; flags/counts are not independently verified accident counts.

Collision messages are prioritized in the queue and include the observed Central timestamp, vehicle, reservation when identified, and SMS status. The queue and trip records commit before sending texts. Texts go to the existing configured SMS receiver via Twilio and honor the SMS enabled setting. A durable claim permits at most one simultaneous send per collision; successful sends are also recorded in `fleet_alert_deliveries`. The send batch is limited to 10 per poll. Disabled/unconfigured SMS and explicit provider rejections retry no sooner than 15 minutes later. Transport timeouts, aborted sends or other ambiguous responses become `uncertain`, because Twilio may already have accepted them; an interrupted `sending` claim becomes uncertain after 10 minutes. These are not automatically resent. Check Twilio delivery history and send manually if needed. This avoids repeated texts but cannot promise exactly-once delivery across an external provider failure. The queue alert remains independently available and its read state is preserved on retries.

Existing Twilio account/sender/receiver settings must be configured and SMS alerts enabled for texts to send. DIMO must share non-location data and all-time location; event/device availability still applies. No live SMS is sent by the automated tests. Log events `[collisions] check complete` summarize vehicles checked, failures, new detections and texts sent; `[collisions] vehicle check failed` identifies a vehicle with a retained checkpoint without exposing provider payloads or credentials. Scheduled detections have no manual import-history entry; their source is the collision monitor.

## Import DIMO incidents on request

Select **Import DIMO incidents** in telemetry review. The browser requests sequential windows of at most 24 hours within the scheduled trip window, capped at the current time. The trip must have an exact `turo_vehicle_id` vehicle link with a DIMO token ID; missing or ambiguous links fail rather than guessing from nicknames. Imports require `trips.read`, `trips.write` and `telemetry.read`. Read-only users can review stored events but cannot import them.

The backend uses DIMO's [documented events query](https://github.com/DIMO-Network/telemetry-api/blob/main/schema/events.graphqls), returning event timestamp, name, source, duration in nanoseconds and metadata. This requires vehicle non-location data and all-time location sharing. It imports all returned event names, including collision/behavior events when the device and provider supply them; it does not manufacture incident classifications. DIMO availability, permissions and retention determine historical coverage.

Imports are serialized per backend process. Provider lookup/auth has a 20-second deadline, responses are bounded at 2 MiB / 2,000 events per window, and database writes use batches of 100 in a short transaction with a 5-second per-statement timeout. No database client is held during provider calls. Oversized, malformed, partial GraphQL, permission-denied and unavailable responses fail explicitly rather than recording an empty success. A successful empty window means only that DIMO returned no events for that request. Import history records requested window, outcome, counts and safe errors; it displays the latest 20 attempts, not a claim of complete historical coverage. A process interrupted mid-import may leave a `running` attempt; retry safely.

**Stop import** stops further requests and cancels the current lookup where possible; completed windows remain saved. **Resume DIMO incident import** continues the current browser session from its last completed window. After a reload, importing starts from the trip beginning, with duplicate protection by vehicle token and provider event fingerprint. Repeated polls or overlapping window boundaries do not duplicate the same returned record. Provider corrections with changed event contents can remain separate records. Structured metadata is credential-redacted recursively; unstructured metadata retains descriptive text while masking labeled authentication values. A provider-reported collision is not independent proof of an accident, causation or driver fault.

Imported events appear in the paged DIMO event list, the full-trip export's `incidents` array (batches of 100), and the AI tool's `incidents` view alongside recent import history. Full-trip exports include already imported events; exporting or asking AI does not contact DIMO or initiate imports. Import first, then ask AI to review the records. The existing full-export `complete` marker describes completion of the local export, not completeness of DIMO's historical records.

The DIMO event list groups records by provider event category (harsh braking, extreme braking, harsh acceleration, harsh cornering, collision detected, and any other returned types). Each category displays its full-trip stored record count and a disclosure caret. Expand a category to load its records, then expand a timestamp to inspect fields. Each category paginates independently in 50-record pages, so the category count includes records beyond the current page. Counts represent stored provider records, not independently verified incidents or metadata counter totals. Unknown event names remain visible under their original names.

## Internal AI questions

Expand **Ask AI to review possible incident or driving behavior** within telemetry review for an editable prompt scoped to the current trip (and selected snapshot when inspecting one). Press **Ask** to send it through the existing internal AI integration and view the cited answer in place. Opening the prompt does not send a request. The prompt asks for specific fields and observation times, distinguishes facts from interpretations, and calls out stale readings, missing data and partial coverage.

The internal AI has a `trip_telemetry` tool backed by these same summary, timeline and snapshot-detail services. It first resolves a reservation number to the internal trip ID using `search_trips`, then can retrieve coverage, page through 50 snapshots/signals at a time, filter by provider or signal name, and inspect a single snapshot's redacted raw payload. For example: "Review the received telemetry for reservation 62331575, including speed and any impact or hard-braking fields."

The AI retains its existing business-questions authorization and database-wide read access. Lookups use one read-only transaction/client with the existing 10-second statement timeout. The existing per-question lookup and result-size limits still apply: partial review must be disclosed, and oversized results are failed lookups, not evidence that telemetry is missing. Answers cite retrieved sources and distinguish never-imported events, failed imports, completed empty windows, unavailable provider history and expired raw payloads from unavailable telemetry access. The AI cannot trigger incident imports.
