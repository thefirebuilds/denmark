# Fleet ownership and shared tracker accounts

Bouncie/DIMO account access is not ownership. Telemetry collection requires an existing active local vehicle matched by exact normalized VIN. Bouncie persistence is update-only and additionally requires that local vehicle's ID and VIN; it cannot insert a new vehicle, reactivate a vehicle, change its website eligibility, or replace an operator nickname with a provider nickname. Shared device IDs and nicknames are not enrollment keys.

The operator has explicitly identified **Blossom, Cocaina, OJ, Phantom, Tulip and Yogi** as outside Denmark's fleet. The shared exclusion policy in `server/services/vehicles/nonOwnedVehicles.js` checks exact case-insensitive names, listing names and active local aliases. Startup retires matching records by setting active, service and trip-eligibility flags false, even if they have a Turo listing ID. Identity and historical data are preserved; no vehicles, trips or telemetry history are deleted. The exclusions also apply to telemetry's managed-vehicle lookup and the public availability output itself. An accidentally populated listing ID or stale active flag cannot make these six cars public.

Both the public pull endpoint and signed website pushes use that filtered availability output. A quick restart republishes the snapshot even if the general 15-minute startup-job cooldown suppresses other jobs, while respecting the public-availability integration enablement setting. Website consumers should replace their prior vehicle list with the received full snapshot rather than retain entries absent from it. Settings → Website → Push Now remains available for an explicit refresh.

Deploy/restart the backend to apply startup retirement and publish the updated snapshot. No schema migration is required. These safeguards are covered by tests with all six excluded records marked active and given numeric listing IDs, renamed records with matching aliases, real fleet vehicles that must remain visible, update-only provider persistence, and startup publication on cooldown. Live website/production database state must still be verified separately; local tests do not establish that a deployment has occurred.
